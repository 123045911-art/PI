1. INTRODUCCIÓN Y METODOLOGÍA
1.1 Objetivo
Identificar vulnerabilidades de seguridad en el sistema Visio Flow, implementar correcciones
directamente en el código fuente, y documentar el proceso con evidencia técnica.

1.2 Alcance
? API FastAPI (puerto 8000): 7 routers, 25+ endpoints
? Flask Vision Service (puerto 5000): 5 rutas + autenticación por sesión
? Infraestructura Docker Compose: 5 servicios
? Base de datos PostgreSQL: esquema y configuración
? Redis: configuración de caché y autenticación

1.3 Metodología
Se siguió el estándar OWASP API Security Top 10 (2023) como marco de referencia.
El análisis se realizó mediante revisión estática del código fuente (SAST manual),
inspeccionando cada archivo de configuración, router, servicio y esquema de datos.
Fases del análisis:
1. Reconocimiento ? listado de endpoints y servicios
2. Clasificación ? categorización por riesgo (CRÍTICA / MEDIA)
3. Explotabilidad ? evaluación del impacto potencial
4. Remediación ? implementación de controles de seguridad
5. Verificación ? revisión post-cambio del código corregido

1.4 Herramientas utilizadas
? Revisión manual de código fuente (Python, YAML, SQL)
? OWASP API Security Top 10 2023 como lista de referencia
? python-jose (JWT HS256) para implementación de tokens
? slowapi para rate limiting
? passlib + bcrypt para hashing (ya existía, validado correcto)

3. HALLAZGOS DETALLADOS (CRÍTICAS)
VF-001 ? Autenticación basada en header HTTP falsificable

CRÍTICA

OWASP: API2:2023 ? Broken Authentication
Componente: API/app/security/auth.py
ANTES (vulnerable):
verify_admin(x_is_admin: bool = Header(False, alias='X-Is-Admin'))

DESPUÉS (corregido):
get_current_user(token) usando JWT Bearer ? python-jose HS256

Impacto:
Fix aplicado:

Cualquier cliente podía enviar X-Is-Admin: true y obtener acceso admin completo.
Reemplazado por verificación criptográfica de JWT firmado con HS256.

VF-002 ? Login no genera token de sesión seguro (sin JWT)

CRÍTICA

OWASP: API2:2023 ? Broken Authentication
Componente: API/app/router/auth.py
ANTES (vulnerable):
LoginResponse(user=UserOut) ? solo retornaba datos del usuario

DESPUÉS (corregido):
TokenOut(access_token=JWT, token_type='bearer', user=UserOut)

Impacto:
Fix aplicado:

Sin token, cualquier endpoint 'protegido' era bypasseable con el header X-Is-Admin.
Login ahora genera JWT HS256 con subject=user_id, is_admin, exp.

VF-003 ? Endpoint POST /events sin autenticación

CRÍTICA

OWASP: API1:2023 ? Broken Object Level Authorization
Componente: API/app/router/events.py
ANTES (vulnerable):
def ingest_event(payload, db) ? sin dependencia de auth

DESPUÉS (corregido):
dependencies=[Depends(get_current_user)]

Impacto:
Fix aplicado:

Cualquier agente externo podía insertar eventos falsos en la base de datos.
Dependencia JWT get_current_user agregada al endpoint.

VF-010 ? Flask secret_key hardcodeada como fallback inseguro

CRÍTICA

OWASP: API8:2023 ? Security Misconfiguration
Componente: contador_personas_flask/app/__init__.py

app.secret_key = os.getenv('FLASK_SECRET_KEY', 'super-secret-key-123')

4. ARQUITECTURA DE SEGURIDAD POST-HARDENING
Flujo de autenticación JWT implementado:
[Cliente / Laravel / Flask]
|
| POST /auth/login {username, password}
v
[FastAPI :8000]
| 1. Valida credenciales contra PostgreSQL (bcrypt)
| 2. Genera JWT HS256 {sub: user_id, is_admin, exp: +60min}
| 3. Retorna {access_token, token_type: 'bearer', user}
v
[Cliente recibe token]
|
| GET/POST /endpoint Authorization: Bearer <JWT>
v
[FastAPI ? get_current_user()]
| 1. Extrae token del header Authorization
| 2. Verifica firma HS256 con JWT_SECRET_KEY
| 3. Verifica expiración (exp claim)
| 4. Retorna payload {sub, is_admin}
v
[require_admin()] ? solo para endpoints de gestión
| Verifica is_admin == True en el payload JWT
v
[Endpoint ejecuta lógica de negocio]

Controles implementados por capa:
? Red / Docker
? PostgreSQL sin puerto expuesto al host (solo red Docker interna)
? Redis con contraseña --requirepass y sin puerto expuesto al host
? Todos los servicios en red privada visioflow-net

? Aplicación ? FastAPI
? JWT Bearer tokens (python-jose, HS256, 60 min TTL)
? Rate limiting: 100 req/min por IP (slowapi)
? CORS: lista blanca explícita de orígenes
? Documentación /docs deshabilitada en producción (APP_ENV)
? Validación de contraseñas: mín. 8 chars, letra + número

? Aplicación ? Flask
? SECRET_KEY obligatoria desde env (error fatal si no definida)
? Cookies de sesión: HttpOnly=True, SameSite=Lax, Secure=True en prod

? Secretos / Configuración
? Todas las credenciales en .env (no en docker-compose.yml)
? .env.example documenta las variables requeridas
? APP_DEBUG=false en producción (Laravel)

5. CONCLUSIONES Y RECOMENDACIONES FUTURAS
5.1 Estado antes del análisis
El sistema Visio Flow en su estado original presentaba 10 vulnerabilidades críticas y 7 medias.
La vulnerabilidad más severa era la autenticación basada en un header HTTP (X-Is-Admin: true)
que cualquier cliente podía falsificar, combinada con la ausencia total de tokens JWT.
Esto implicaba que un atacante con acceso a la red podía:
? Insertar eventos falsos en la base de datos
? Leer todos los datos de heatmap y dashboard
? Crear/eliminar áreas y usuarios
? Acceder a Redis sin autenticación y manipular sesiones
? Conectarse directamente a PostgreSQL (puerto 5435 expuesto) con contraseña '123456'

5.2 Estado después del análisis
Tras las implementaciones, el sistema cuenta con:
? Autenticación JWT obligatoria en todos los endpoints sensibles
? Verificación criptográfica de roles (is_admin en JWT payload)
? Rate limiting activo (100 req/min por IP)
? CORS configurado con lista blanca
? Secretos externalizados en variables de entorno
? Base de datos y Redis no accesibles desde el exterior
? Contraseñas con complejidad mínima validada
? Debug deshabilitado en producción

5.3 Recomendaciones futuras (fuera del alcance actual)
? Implementar refresh tokens para renovación sin re-login
? Agregar rate limiting específico más estricto en /auth/login (ej. 5 req/min)
? Implementar HTTPS/TLS con certificados (nginx reverse proxy)
? Agregar logging de auditoría para intentos de login fallidos
? Implementar Content Security Policy (CSP) en el dashboard Laravel
? Realizar análisis de dependencias (OWASP Dependency Check)
? Considerar secrets management dedicado (HashiCorp Vault o similar)
? Agregar pruebas de seguridad automatizadas al pipeline CI/CD

RESULTADO FINAL
17 vulnerabilidades identificadas ? 17 corregidas
